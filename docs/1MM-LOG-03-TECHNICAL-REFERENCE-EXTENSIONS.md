This log is the public record of every addition and correction made to the Technical Reference after
its v3.5 baseline. Open it before you build something a module plan marks as a gap, to see whether
the gap was applied, is waiting for the owner, or was rejected; and open it when you write the
migration that carries schema change set 0007.

## 1. How this log works

The owner's rule: every addition extends from the Technical Reference. The reference is updated
first, then the change is extended into the documents, the migrations and the schema.

1. A document that needs something the Technical Reference, the schema or the UI lacks raises a gap
   in its own "Gaps raised" table ([1MM-STD-02](standards/1MM-STD-02-AGENTIC-OPERATIONS.md)).
2. Gaps of type `TR` or `SCHEMA` are verified against the Technical Reference and the baseline
   schema, merged where several documents describe the same thing, and recorded in the Technical
   Reference section 20 as an extension `TRX-nnn` [TR §20.1].
3. The Technical Reference master is in the private specification pack and is not in this
   repository. This log mirrors section 20: it summarises each extension, and it holds the exact
   schema change set and the gap index. Where the two differ, the Technical Reference wins and this
   log is corrected.
4. Gaps of type `UI`, `DECISION` and `REPO` are tracked in their own logs
   ([1MM-LOG-02](1MM-LOG-02-UI-UPDATES.md) for design boards); a mixed-type gap appears here for its
   `TR` or `SCHEMA` part only.

**Dispositions.** _Applied (v3.6)_: written into the Technical Reference; build to it. _Applied
(v3.6) + schema change_: as above, with DDL or seeds in change set 0007 (section 3). _Proposed,
awaiting owner decision_: not in the Technical Reference as fact; the recommended default is what
plans assume meanwhile. _Deferred_: belongs to a feature that is off at launch. _Rejected_: not a
gap in the Technical Reference, with the reason.

**To add an entry.** Raise the gap in your document; the engineering lead records the extension in
the Technical Reference, then adds a register row here with the next free `TRX` id, adds any
schema change to the next change set, and adds the gap id to the index in section 7. Ids are never
reused. A decided "Proposed" entry keeps its id and changes disposition, with a change-log row.

**Counts at v1.0.** 225 gaps of type `TR` or `SCHEMA` (out of 371 gaps collected) collapse into 107
extensions: 66 applied (TRX-001 to TRX-066; 9 of them with a schema change in set 0007), 37 awaiting an owner
decision, 1 deferred, 3 rejected.

#### SC-02 · `decide_intro()` reads the cooldown from config and runs as definer (TRX-044, TRX-048; GAP-MOD08-03, GAP-DB05-02)

The body is the baseline body with three differences: the definer clause, the actor guard as the
first statement, and `make_interval(days => config_int('discovery.pass_memory_days', 30))` in
place of both `interval '30 days'` literals.

```sql
CREATE OR REPLACE FUNCTION decide_intro(p_session uuid, p_user uuid, p_decision intro_decision_t)
RETURNS text LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_temp AS $$
DECLARE s intro_sessions%ROWTYPE; v_keep int; v_n int; v_cid uuid;
BEGIN
  IF app_current_user_id() IS NOT NULL AND p_user IS DISTINCT FROM app_current_user_id() THEN
    RAISE EXCEPTION 'actor mismatch' USING ERRCODE = '42501';
  END IF;
  SELECT * INTO s FROM intro_sessions WHERE id = p_session FOR UPDATE;
  IF NOT FOUND OR p_user NOT IN (s.user_a, s.user_b) THEN
    RAISE EXCEPTION 'not a participant' USING ERRCODE = '42501';
  END IF;
  IF s.status IN ('decided','expired') THEN RETURN s.outcome; END IF;
  INSERT INTO intro_decisions (intro_session_id, user_id, decision) VALUES (p_session, p_user, p_decision)
  ON CONFLICT DO NOTHING;
  SELECT count(*), count(*) FILTER (WHERE decision = 'keep') INTO v_n, v_keep
    FROM intro_decisions WHERE intro_session_id = p_session;
  IF v_n < 2 AND p_decision = 'keep' THEN RETURN 'waiting'; END IF;

  IF v_keep = 2 THEN
    INSERT INTO conversations (kind, user_a, user_b, match_id, intro_session_id, state, opened_via)
    VALUES ('match', s.user_a, s.user_b, s.match_id, s.id, 'open', 'both_keep')
    RETURNING id INTO v_cid;
    INSERT INTO conversation_participants (conversation_id, user_id) VALUES (v_cid, s.user_a), (v_cid, s.user_b);
    UPDATE intro_messages SET kept = true WHERE intro_session_id = p_session;
    UPDATE intro_sessions SET status = 'decided', outcome = 'both_keep', decided_at = now() WHERE id = p_session;
    RETURN 'both_keep';
  END IF;

  UPDATE intro_sessions SET status = 'decided', outcome = 'moved_on', decided_at = now() WHERE id = p_session;
  UPDATE matches SET status = 'moved_on', ended_at = now(), ended_reason = 'moved_on', ended_by = p_user WHERE id = s.match_id;
  INSERT INTO pair_cooldowns (user_id, other_id, reason, until) VALUES
    (s.user_a, s.user_b, 'moved_on', now() + make_interval(days => config_int('discovery.pass_memory_days', 30))),
    (s.user_b, s.user_a, 'moved_on', now() + make_interval(days => config_int('discovery.pass_memory_days', 30)))
  ON CONFLICT (user_id, other_id, reason) DO UPDATE SET until = EXCLUDED.until;
  RETURN 'moved_on';
END $$;
REVOKE EXECUTE ON FUNCTION decide_intro(uuid, uuid, intro_decision_t) FROM PUBLIC;
```

Before writing the file, diff this body against the baseline function (line 5700 of the baseline)
and confirm the three differences are the only ones. `CREATE OR REPLACE` keeps the existing
comment on the function.

- **Status.** Implemented in `0007_trx_schema_change_set.sql`, tested (cooldown 30 days by default and 7 days with the key changed; both-keep as the member login creates the conversation and both participant rows). The guard differs from the block above: deviation 1 in section 3.4.
- **Why it is safe.** With the seeded value (30) the behaviour is unchanged; `unmatch()` already
  uses the same pattern for `unmatch.cooldown_days`. The definer part is explained in SC-06.
- **Test.** (1) Default: a moved-on decision writes two `pair_cooldowns` rows with `until`
  30 days ahead. (2) In a test transaction set `discovery.pass_memory_days` to 7 and assert

  tests 2 and 3 for this function.

### 3.4 Implementation record and deviations

Migration: `packages/db/migrations/0007_trx_schema_change_set.sql` (one file; no enum value is
added, so no split was needed). Verified on PostgreSQL 16 + PostGIS 3.4 on 24 Nov 2026: applied
to an empty database after `0001` and `0006`; `pnpm db:migrate` a second time prints "database is
up to date"; the file's SQL executed a second and third time changes nothing and keeps the
grants; `pnpm db:roles` twice.

Counts after the migration, by catalogue query against a database migrated to `0006` and one
migrated to `0007`: tables 221 (unchanged); partitions 121 → 135; indexes including partitions
1,085 → 1,125 (12 new, 28 on the new partitions); functions 40 (unchanged), `SECURITY DEFINER`
functions 2 → 6; policies 14 (unchanged, one altered); `remote_config` keys 86 → 97 (public 41 →
47); `worker_jobs` rows 66 → 70 (4 with a `cron`).

Deviations from the SQL printed in section 3.1:

1. **Actor guard (SC-02, SC-06).** As printed, the guard let every caller with no member context
   through ("the worker calls with no member context"). The member role is granted `EXECUTE` too,
   so a member API transaction that did not set `app.user_id` could have acted as any member:
   the same fail-open that SC-05 removes from `profiles_read`, and before this change row-level
   security refused exactly that. The implemented guard keeps the printed rule when a member
   context is set (the actor argument must equal it, else 42501 "actor mismatch"), and with no
   member context allows the call only when the session's login has `BYPASSRLS` (the worker and
   admin logins; the attribute belongs to the login) or is, or is a member of, the role that owns
   the function (migrations, owner-run tests); any other login gets 42501 "member context
   required". `session_user` is used because inside a definer function `current_user` is the
   owner. Tested: the member login with no context is refused in all four functions, including
   `unmatch(<match>, NULL)`, which the printed guard and the baseline participant check would both
   have let through; the worker login with no context runs the full flow.
2. **SC-03 `DO` block.** The block drops every CHECK whose definition contains `respond_by = `
   in a loop, where the printed block took the first one. Same result on the baseline (there is
   one, `safety_checkins_check`).
3. **Grants (SC-06).** `app_admin_api` is not granted `EXECUTE` on the four matching functions,
   as printed. No module plan has the admin API call them; a test asserts the refusal. Adding it
   is one line in `roles.sql`.
4. **Models and `pnpm db:pull`.** No Drizzle model in `packages/db/src/schema/` (`remote_config`,
   `feature_flags`) references a column or object this set changes, so no model changed.
5. **Tests listed in section 3.1 that are not in the migration's test file** because they need
   code that does not exist yet: the API validation of `deletion.grace_days` and the public
   config response (MOD-02), the web safety report SLA (MOD-14), the erasure cascade plan
   (MOD-16), and the owner-run behaviour tests and parallel-connection matching test
   (`MOD-00-DB-02`).

Follow-ups this leaves open: per-module row-level security (TRX-054, GAP-DB05-01) is unchanged;
`spend_spec_view()` and `redeem_beta_invite()` were named in GAP-DB05-02 "after review" and are
not in this set.
