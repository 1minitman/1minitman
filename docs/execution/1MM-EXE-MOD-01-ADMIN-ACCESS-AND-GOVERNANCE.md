**What this document is for and when to open it.** It plans everything that decides who may use
the admin console and what is recorded when they do: sign-in, MFA, step-up, sessions, allow-lists,
break-glass, roles and permissions, four-eyes approvals, the hash-chained audit log and admin
user management. Open it before building any admin endpoint, because every later module calls
the permission check, the approval engine and the audit writer defined here.

## 1. Outcome

When this module is done:

- **For an admin:** a member of staff accepts an invite, sets a password of at least 12
  characters, enrols a passkey or TOTP factor, saves recovery codes and signs in with two factors
  [ADM A02], [OD-07]. The console locks after 30 minutes idle and ends after 8 hours [TR §7.1].
  Sensitive actions ask for a reason, a fresh second factor or a second admin, exactly as the
  permission's three flags say [ADM §1.2]. A super admin manages roles, grants, approvals and
  staff, and reads and exports the audit log [ADM A05–A08].
- **For a member:** nothing visible, except that the name they see in support chat (H1B) is the
  agent's `admin_users.display_name` [ADM A08]. No member credential opens the console and no
  admin cookie opens `/v1` [ADM A02].
- **For the business:** every admin write and every reveal of personal data is one row in an
  append-only, hash-chained log kept for 7 years, verified nightly [TR §7.1]; no admin can sign in
  without a second factor (`v_admin_mfa_gaps` is empty) [TR §7.1]; no approval is ever
  self-approved [SQL]; one dormant break-glass account exists and its grants last at most 4 hours
  [TR §7.1].

## 2. Scope

**In scope.** Admin modules A02, A03, A05, A06, A07, A08 [ADM]; the `/admin/v1` groups "Access"
and "Governance" [TR §8.2]; the authorisation pipeline of [ADM §1.1]; the approval engine and the
audit writer as services every module uses [ADM §1.2], [ADM §1.3]; the authenticated
`GET /admin/v1/stream` [ADM §1.6]; the console export pipeline (`admin_exports`), first used by
the audit export [ADM A07]; jobs `audit.verify_chain`, `approvals.expire`, `exports.admin.build`,
`exports.admin.purge` [SQL `worker_jobs`].

**Out of scope.**

### 4.3 Rules the API must enforce

**Authorisation pipeline.**

1. Every `/admin/v1` request checks, in order: session live (`revoked_at IS NULL`,
   `idle_expires_at > now()`, `expires_at > now()`), admin `status = 'active'`, permission held
   now (`v_admin_effective_permissions`), scope matches the target, IP allowed, and fresh MFA for
   `requires_reauth` permissions [ADM §1.1].
2. A missing permission returns `403 {reason:"permission", permission}`; a row outside the
   admin's scope is left out of lists and returns 404, never 403 [ADM §1.1].
3. With an allow-list set, a request from outside it is refused on every `/admin/v1` route,
   sign-in included [ADM A03].
4. A member token is never accepted on `/admin/v1` and the admin cookie is never accepted on
   `/v1` [ADM A02].
5. `requires_reason`: the reason is 5 to 2,000 characters and is stored in
   `admin_audit_log.reason` [ADM §1.2].
6. `requires_reauth`: refused with 403 `reauth_required` unless MFA was verified in the last 5
   minutes; a password never
   satisfies step-up; after step-up the original request completes once, with the same
   `Idempotency-Key` [ADM A03].
7. `requires_approval`: the action does not execute; it creates an `admin_approvals` row with the
   exact change as `payload` and returns 202 with `approval_id` and `expires_at` [ADM §1.2],
   [1MM-STD-13](../standards/1MM-STD-13-ERROR-CODES.md) §4.6.

**Sign-in and factors.**

8. Wrong email and wrong password give the same message and the same timing (± 50 ms padding)
   [ADM A02].
9. Every step writes `admin_login_attempts` with `email_hash` = SHA-256 of the normalised email
   [ADM A02].
10. Ten failed attempts in 15 minutes for one account + IP lock it for 30 minutes
    (`rate_limit_policies.admin.login`); wrong MFA and recovery codes count towards it
    [ADM A02], [SQL].
11. No session is created for an admin without a confirmed factor (`v_admin_mfa_gaps`); there is
    no path that signs in without a second factor [TR §7.1], [ADM A02].
12. TOTP: ±1 time step, each code usable once [ADM A02].
13. WebAuthn: `userVerification: required`; a sign-count regression refuses sign-in and raises a
    `passkey_anomaly` alert [ADM A02], [SQL].
14. The last confirmed factor cannot be removed [ADM A02].
15. Recovery codes: exactly 10 per batch, stored as digests, single use; using one forces a new
    factor before anything else; a new batch revokes the old one [ADM A02], [SQL].
16. Invite tokens are single-use and expire after `admin.invite_valid_hours`; `status` becomes
    `active` only after MFA is confirmed [ADM A02], [SQL].
17. Passwords: Argon2id; at least `admin.password_min_length` and at most 128 characters; not in
    the breached list; not containing the email local part or "1minit"; not equal to the current
    one [ADM A02], [TR §13.2].

**Sessions.**

18. Idle 30 minutes, moved forward only by `POST /auth/keep-alive` from real user activity;
    absolute 8 hours with no extension (CHECK) [ADM A03], [SQL].
19. The cookie is HttpOnly, Secure, SameSite=Strict; only `token_hash` is stored [TR §7.1], [SQL].
20. A revoked session is refused on the next request and the stream sends `session.revoked`
    [ADM A03].
21. Revoking another admin's session needs a reason and re-auth but no approval [ADM A03].
22. Alerts: the seven rules in `admin_security_alerts.rule` are evaluated on each attempt and
    session insert; each hit notifies the admin and super admins [ADM A03], [TR §7.1].
23. "This wasn't me" revokes all that admin's sessions, locks the account at once with
    `lock_reason = 'security_alert'` and opens a security incident, without approval; blocking
    the network still goes through `security.ip_lists` approval [ADM A03], [SQL], [DDR].
24. Break-glass: activation needs two people; the grant is `super_admin` for at most 4 hours
    (CHECK) and is not counted against `max_holders`; MFA still applies; every action is tagged
    `after.break_glass = true`; closing revokes the grant and sessions, suspends the account and
    opens a review incident [ADM A03], [SQL].

**RBAC.**

25. `super_admin` holds every permission; a migration that adds a permission grants it to
    `super_admin` in the same migration [ADM A05].
26. System roles cannot be renamed, retired or edited; custom roles are cloned from them
    (AD-15 in [ADM App. D]).
27. `max_holders` is checked on every grant against live, unexpired grants [ADM A05].
28. Nobody changes their own grants or the permissions of a role they hold [ADM A05].
29. A grant's scope must be one of the permission's `allowed_scopes`; `scope_value` is NULL
    exactly when the scope is `global` or `own` (CHECK) [SQL].
30. A time-boxed grant stops working at `expires_at` with no job, because the view filters it
    [ADM A05], [SQL].
31. A retired role's permissions leave `v_admin_effective_permissions` immediately [ADM A05].

**Approvals.**

32. The requester can never decide their own request: hidden in the UI, 403 `approval_self` in the API, CHECK in
    the database [ADM A06], [SQL].
33. An approver needs `approvals.decide` and the request's own `permission_key`, within scope;
    when `approver_id` is set only that admin may decide [ADM A06], [SQL].
34. Approval re-validates the payload against the current state and refuses if the target
    changed since the request [ADM A06].
35. An approved request executes exactly once, in the same transaction as its audit row; a
    provider failure sets `failed` with `execution_error` and can be retried idempotently
    [ADM A06], [SQL].
36. Requests expire after 72 hours and cannot then be approved [ADM A06].

**Audit.**

37. One `admin_audit_log` row per write, per PII reveal and per evidence view, in the same
    transaction as the change, with `permission_key`, `reason`, `approval_id`, `before`, `after`
    (changed fields only, personal fields masked), `ip`, `user_agent`, `request_id` [ADM §1.3].
38. The log is never updated or deleted; `app_admin_api` has no UPDATE or DELETE on it
    [SQL], `packages/db/roles/roles.sql`.
39. Audit queries need a date range of at most 31 days so partitions are pruned [ADM A07].
40. Exports include `prev_hash` and `row_hash`; the link is signed and valid 24 hours
    [ADM A07], [ADM §1.4].

**Admin management.**

41. Deactivation revokes sessions, live grants and factors and releases the admin's work through
    a `QueueReassigner` port; each owning module registers its reassigner as it is built
    [ADM A08].
42. An admin cannot act on their own account in A08; the last active `super_admin` cannot be
    suspended or deactivated [ADM A08].
43. MFA reset is approved only by a `super_admin` other than the requester [ADM A08].
44. While a security incident linked to a locked admin is open, an early unlock needs a second
    admin's approval [OD-29].
45. Work e-mail must be on the staff domain; invites carry no role details (AD-01 in
    [ADM App. D]), [ADM A08].
