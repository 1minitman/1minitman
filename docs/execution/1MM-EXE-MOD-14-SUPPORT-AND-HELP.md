This is the execution plan for in-app help, feedback and support chat, the admin support inbox and
help-centre authoring, and the website help centre, contact form and safety report form. Open it
before building any `/v1/help`, `/v1/support`, `/v1/feedback`, `/admin/v1/support`, `/admin/v1/help`
endpoint, or the public `contact` and safety-report endpoints, and whenever a change touches the
website form pipeline that MOD-15 reuses.

## 1. Outcome

| For               | What is true when this module is done                                                                                                                                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A member          | Finds an answer in H1 by search, topic or popular article; reads steps in H1A and jumps to the right screen; votes "Was this helpful?"; chats with a named human agent in H1B and is notified of the reply (N30); sends a 1–5 rating with optional text [UF §15.11], [INV H1, H1A, H1B].      |
| A website visitor | Searches the help centre in en, pcm or fr without JavaScript (W32); sends a contact request and gets a reference by email (W33); reports a safety issue, anonymously if they wish, and sees an `SR-n` reference, even while the site is in maintenance (W34) [WEB W32–W34], [OD-32], [OD-40]. |
| An admin          | Works chats, email and web-form tickets in one inbox with a 2-hour first-response target, writes internal notes that never reach the member, uses macros, authors and reviews help articles in three locales, and reads feedback [ADM A27].                                                   |
| The business      | Urgent web safety reports reach trust and safety inside the 60-minute target; privacy requests reach the DPO register with a `PR-n` reference; help content has one source for the app and the website [WEB W34], [WEB W33], [WEB W32].                                                       |

### 4.3 Rules the API must enforce

1. Member help reads return only the live revision of a `published` article; a locale with no published row falls back to `en` and says so [SQL], [WEB W32].
2. An article cannot be published without `last_reviewed_at`, and never by its last editor; a safety-category article needs a `content.review_safety` approver; `pcm` and `fr` rows need a native review [SQL] `ck_help_reviewed`, [ADM A27], [DD §13A.2].
3. One vote per member per article (`uq_help_vote_user`); the API keeps `helpful_yes` / `helpful_no` in step with the votes in the same transaction [SQL].
4. A new ticket sets `reply_due_at = created_at + support.first_response_hours`; the first agent reply sets `first_response_at` [DD §11].
5. Internal notes are never returned by, or pushed through, any member route [ADM A27].
6. A member reads and writes only tickets where `user_id` is their own; another id answers 404. There is no RLS on these tables, so the check is in the application layer and has a test per route [SQL].
7. The agent's name shown to the member is `admin_users.display_name`, never the email or real name [DD §13].
8. A member message moves the ticket to `pending_agent`; an agent reply to `pending_member`; "Solve" sets `solved_at` [ADM A27].
9. Merge requires the same member and writes `merged_into_id`; a ticket cannot merge into itself [SQL], [ADM A27].
10. Tickets with `channel = 'safety'` are routed to trust and safety; agents cannot open report evidence or member chats from the inbox [ADM A27].
11. The composer warns when agent text matches "password" or "code"; agents never ask for them [ADM A27].
12. Ticket priority: higher number is more urgent; queue order is priority descending, then created ascending [DDR B33], [ADM A27].
13. Every public form request passes: content type, origin, per-form token, honeypot, minimum time-to-submit, payload size, HTML stripped, `Idempotency-Key`, `public.forms` limit. No CAPTCHA [WEB §3.12], [WEB §5.10].
14. While `site_settings.maintenance.enabled` is true, every form route answers 503 `maintenance` with `Retry-After`, except forms named in `exempt_forms` (the safety report) [OD-32], [WEB W38].
15. A contact submission needs name and email; a safety report does not (`ck_contact_identity`) [SQL].
16. A safety report gets `SR-n`, priority `urgent` for `under_18` and `threats_violence`, and `sla_due_at` from the two config keys; the database trigger is the source of truth [SQL].
17. Routing at submit: `safety` → a ticket with `channel = 'safety'` and, when urgent, a case through MOD-09's port plus an admin notification; `data_request` → a `privacy_requests` row (`source = 'web_form'`, `due_at` from `privacy.sla_days.*`); `support` → a ticket with `channel = 'web_form'` and `ticket_id` set; other kinds stay `new` for A29 [ADM A29], [WEB §5.6].
18. Responses never echo personal data beyond what was just typed; the safety response returns the reference only [WEB §5.10], [WEB W34].
19. The web form never changes an account and never releases data; identity for a privacy request is verified later, off the website [WEB §5.6].
20. An upload is usable only when `scan_status = 'clean'`; images have EXIF stripped; counts are capped at 3 (contact) and 5 (safety) [TR §6.1].
21. The stored `ip_prefix` is truncated; no full IP is kept with a submission [DD §13B.2], [WEB §3.11].
22. No name, email, free text or report detail is sent to analytics; the W34 page loads no third-party script even with consent [WEB §3.11], [WEB W34].
