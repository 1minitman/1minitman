This is the execution plan for Groups: discovery, the group room and its chat, group info, the
five-step create flow, the groups empty states, and group moderation in the admin console. Open it
before building any group endpoint, event, job or screen, and when reviewing a pull request that
touches them. Group events (meet-ups of kind `group`) and venues are planned in MOD-13.

## 1. Outcome

| For          | What is true when this module is done                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A member     | Every member can browse and read groups; Premium and Gold members post; Premium owns 1 group and Gold 10 [TR §9], [UF §15.9]. A Premium or Gold member creates a group in five steps (basics, privacy and rules, invite, review, created) and it becomes public only after staff approve its name [UF §15.10], [ADM A18]. A member joins, reads along, posts where the plan allows, reacts, mutes, invites people they have matched or chatted with, reports a group and leaves with a confirm [TR §2.3], [DD §7]. |
| An admin     | Staff with `groups.moderate` review new groups, ask for a rename, pause, remove and transfer ownership, each with a reason and an audit row; they never read live room messages [ADM A18]. Limits and labels in the flow change in the console without a release (section 3.4).                                                                                                                                                                                                                                    |
| The business | Groups stay verified-only interest rooms with contact details kept out of names and rules [CN group-rules], [TR §13.4]. Plan gates match the entitlement matrix exactly [TR §9]. The tab can be switched off with one kill switch (`groups.enabled`) [SQL].                                                                                                                                                                                                                                                        |

## 2. Scope

**In scope**

- Member API group "Groups" of [TR §8.2]: list and search, create, read, edit, delete, join, leave, mute, messages, invites, member approval and removal.
- Group chat delivery over the realtime gateway: server event `group.message.new` [TR §8.3].
- Mobile screens D12, D13, D13A, GC1–GC5 and ES4; flow rows 15.9 and 15.10; the ES4 part of row 15.21 (ruling R19).
- Admin A18, groups part: `/engagement/groups` and `/engagement/groups/:id` [ADM A18], [ADM App. B].
- Retention work for group data [DD §7].

### 4.3 Rules the API must enforce

1. With `groups.enabled` off, every route of 4.1 answers 404 and no event is sent [SQL].
2. Create needs Premium or Gold and fewer owned groups than `groups.own_max` (1 or 10); otherwise 403 `entitlement` with the upsell target D15 [TR §9], [UF §15.10]. Owned groups are counted on `owner_id` with `deleted_at IS NULL`.
3. A name is 3–40 characters and carries no phone number, e-mail, link or @handle; the API runs the `contact_details` rule and the database CHECK is surfaced as a readable 422, never a 500 [CN group-rules], [ADM A18], [DDR M37].
4. Description ≤ 140; up to 5 owner rules of 3–80 characters, positions 1–5, each run through the same filter (`group_rule`) [SQL], [UF §15.10].
5. Create requires the guidelines confirmation and stores `guidelines_accepted_at` [UF §15.10], [SQL].
6. A new group is `pending_review`, is created with a `group_review` moderation case, and is hidden from discovery and search until approved [ADM A18].
7. Create writes the owner's `group_members` row (`role = 'owner'`, `status = 'active'`, `joined_at`) in the same transaction; exactly one active owner exists at all times [SQL `uq_group_one_owner`].
8. Join rules: `public` joins at once; `ask` creates `pending_approval` with `requested_at` until an owner or admin approves; `invite` groups are never listed and are joined only through an invite [CN group-rules], [SQL].
9. `member_count` changes in the same transaction as the membership change; a join that would exceed `max_members` is refused with 409 [SQL].
10. Posting needs `groups.post`, or the owner / admin role when `post_rule = 'admins'`; a Free member gets 403 `entitlement` with Premium pre-selected [TR §8.2], [UF §15.9].
11. A member with a live restriction whose scope includes `group_posts` gets 403 `restricted` on post [SQL `account_restrictions`], [CN].
12. A message body is ≤ 2,000 characters and passes the abuse-rule evaluator (rules that apply to `message`); a refused message is not stored [SQL], [TR §13.4].
13. A replayed `clientMsgId` returns the original message and stores one row [TR §5.3] (storage per GAP-MOD12-03).
14. Each post increments `unread_count` for every other active member and clears nothing else; muted members get no push [SQL], [DD §7].
15. Invites go only to people the inviter has matched or chatted with, at most `groups.invite_batch_max` per request; an invite is a request, not an add [TR §8.2], [CN group-rules], [DDR M41].
16. One pending invite per group and invitee; only the invitee answers it; an expired or answered invite cannot be accepted [SQL].
17. Leave sets `status = 'left'` and `left_at`, and decrements the count [SQL].
18. Only the owner edits or deletes; a renamed group returns to review (GAP-MOD12-10 fixes the detail) [TR §8.2], [ADM A18].
19. A blocked pair never see each other's group messages or member rows; a block hides both people in Groups [CN safety-rules].
20. Reactions: one emoji per member per message; every member may react, posting still needs Premium [DDR M6].
21. Admin approve, pause, remove and transfer each need `groups.moderate`, a reason, and a scope that covers the group's city; each writes its audit event [ADM A18], [ADM App. A.3].
22. No admin route returns `group_messages.body`; only counts of flagged messages [ADM A18, AD-11].
23. Lists use keyset pagination, never OFFSET [TR §8.1].
24. Message bodies never appear in logs, traces or analytics [TR §14].
