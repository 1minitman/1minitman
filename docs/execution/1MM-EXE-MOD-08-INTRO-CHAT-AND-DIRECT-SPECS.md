This is the execution plan for everything that happens after a match: the 1-Minute Intro, the
keep-or-move-on decision, one-to-one chat, Direct Specs and message requests, the failed-send
state, and (deferred) calls. Open it before building any endpoint, socket event, job or screen in
that area, and when reviewing a pull request that touches them.

## 1. Outcome

| For          | What is true when this module is done                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A member     | A match or maybe-match can be opened within 24 hours [OD-02]. Both people get one 60-second window that starts when both are present, send one text or one voice note of up to 20 s each, then choose privately to keep talking or move on [TR §8.4], [UF §15.19]. Both keep: a chat exists. Premium and Gold members chat in it with reactions, replies and effects; Gold sees read receipts; Gold can send Direct Specs; anyone can accept or decline a message request [TR §9], [UF §15.8]. A message that cannot be sent is shown as failed with its reason and is never queued silently [TR §4.2]. |
| An admin     | Every limit, timer, effect and label in the flow is changed in the admin console without a release (section 3.4). Calls stay off behind `calls.enabled` until the owner switches them on [OD-20].                                                                                                                                                                                                                                                                                                                                                                                                       |
| The business | The intro promise ("respect for time") is enforced by the server, not the client [TR §1]. Plan gates match the entitlement matrix exactly [TR §9]. Chat delivery meets the budget of under 500 ms between two online members in one region [TR §15.1].                                                                                                                                                                                                                                                                                                                                                  |

## 2. Scope

**In scope**

- Reading matches and fresh matches (`GET /v1/matches`), the intro lifecycle (open, message, decision, skip), unmatch [TR §8.2].
- Conversations: list, search, thread, send, read, reactions, delete, mute, archive, shared media [TR §8.2].
- Direct Specs and message requests (accept, decline), including the weekly quota and the cross-border limit [TR §8.2], [TR §13.3].
- The Gold fair-use soft cap [OD-31].
- Message-not-sent (ES6), `message_failures`, and the client outbox rules for this module's actions [TR §4.2], [CN states-rules].
- WebSocket events for intro, message, read, typing and request [TR §8.3].
- Jobs `intro.expire`, `intro.audio.purge`, `dm.expire` [TR §11].
- Mobile screens D6, D8, D9, D10, D11, H7, H8, MF2, MF3, MF4, MF5, ES3, ES6 and flow row 15.8.

### 4.3 Rules the API must enforce

1. A match must start its intro within `intro.window_hours` (24 h); the same window applies to maybe-matches [OD-02].
2. The 60 s timer starts only when both people have the intro open (`intro:presence:{session_id}`); `started_at` requires both `a_opened_at` and `b_opened_at` (table CHECK) [TR §8.4], [DD §14].
3. Each person sends exactly one intro message: text up to `intro.text_max_chars` or one voice note up to `intro.voice_max_seconds`. It is not a live chat [DD §5], [DDR M33].
4. Intro voice notes are stored as Opus, transcribed for moderation and deleted after 30 days unless both kept talking [TR §11], [TR §16.1].
5. Decisions are blind and final: a member never learns the other person's choice before making their own, and a decision cannot be changed [TR §8.4].
6. Both keep creates the conversation and marks intro messages `kept`; any Move on ends the match and hides the pair both ways for the move-on period [TR §8.4].
7. A Free verified member can complete the intro but not chat: after `both_keep` they receive the Premium upsell and the intro is saved [TR §9], [UF §15.19].
8. Sending needs `chat.full`; Premium holds at most 20 open conversations; Gold is unlimited [TR §9].
9. Gold fair use: after `chat.gold_new_conversations_daily_soft_cap` new conversations in a day the member gets a gentle message; existing chats are never blocked [OD-31].
10. Skip intro needs `chat.skip_intro` (Premium and Gold) [TR §9].
11. Message effects need `chat.message_effects`, and the effect must be an active `message_effects` row whose `min_role` the sender meets [OD-39].
12. Read receipts are shown only to viewers with `chat.read_receipts` (Gold); the sender of a message request never sees read status before acceptance [DD §6], [UF §15.8].
13. A restricted member gets `403 restricted` on new threads and Direct Specs; replies in existing chats still work [TR §8.2], [SQL] (`account_restrictions` comment).
14. Money, bank, gift-card, crypto and move-app phrases in early chats are blocked (ES6) or the receiver is warned; a blocked message is never stored in `messages` (CHECK `safety_verdict <> 'blocked'`) and is never auto-resent [TR §13.4], [SQL].
15. A `message_failures` row stores a hash, never the body [DD §6].
16. Direct Specs: Gold only, 20 per ISO week, at most 2 abroad in the first 7 days of Gold; the note is 1–200 characters and passes the contact-detail filter [TR §13.3], [TR §13.4].
17. One pending request per sender and recipient, and one live thread per pair (`uq_dm_pending_pair`, `uq_conv_live_pair`) [SQL].
18. Accepting a request uses a conversation slot; likely spam lands in Filtered [UF §15.8].
19. Unmatch closes the chat for both people, cannot be undone, and hides the pair for `unmatch.cooldown_days` [TR §8.4], [DD §13B.3].
20. Either person blocking the other refuses every write in this module for that pair (`is_blocked_pair()`) [TR §8.4].
21. Messages: 30 a minute and 1,000 a day per member [TR §13.3].
22. Messages and reactions carry client-generated ids and replays return the original result [TR §5.3].
23. Member text is stored and rendered as text; no auto-links in chat [TR §13.1].
24. Message bodies never appear in logs [TR §14].
25. Calls are possible only inside an existing chat, are never recorded, start with the camera off on the incoming side and always show the safety banner; with `calls.enabled` off MF4 shows "Coming soon" [UF §15.19], [OD-20].
