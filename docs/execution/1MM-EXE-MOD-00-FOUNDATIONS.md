**What this document is for and when to open it.** It turns the scaffolded monorepo into a real
platform: hosted environments, deploys, the API's cross-cutting machinery, the realtime gateways,
the media base, the worker's job framework, observability, budgets, the shared pipelines, the test
harnesses, and the empty shells of the admin console, the website and the app. Open it before
any feature module starts, and whenever a feature needs a platform capability and you want to
know whether it already exists.

## 1. Outcome

When this module is done:

- **For an engineer or agent:** a pull request merged to `develop` is deployed to a staging
  environment that is separate from production in every resource [TR §4.4]. Any feature module
  can add an endpoint, a job, a console page, a website page or an app screen without building
  plumbing first, and every such addition is tested by a harness that already runs in CI.
- **For an admin:** the console opens on the staging admin host with the design system gallery
  at `/_design` [ADM A01] and the app shell frame [ADM A04]: navigation groups, environment badge,
  theme and density, breadcrumbs, shortcuts, and the standard loading, empty, error and offline
  states [ADM §1.5]. Sign-in and permissions arrive with MOD-01.
- **For a visitor:** the empty website shell on the staging site passes every milestone M1 gate
  in both themes and three locales, with security headers, an offline page and static error
  pages [WEB §7], [WEB W38], [WEB W39].
- **For a member:** the app starts on the splash with the LogoRing, shows the offline state when
  there is no network, and lands in a five-tab shell with the menu drawer and a network banner
  [INV A0], [INV A0·E], [INV ES5], [INV D3], [TR §5.1].
- **For the business:** the platform runs on the free and pay-as-you-go tiers the owner chose
  [OD-06], [OD-11], logs nothing it must not log [TR §14], and measures itself against the
  performance budgets from the first deploy [TR §15.1].

### 4.2 Realtime, jobs and webhooks

**WebSocket gateway (`/v1/ws`).** One socket per signed-in device [TR §4.2]. The gateway owns:
upgrade and authentication, the connection registry (`ws:conn:{user_id}`), Redis pub/sub relay on
`ch:user:{user_id}` and `ch:conv:{conversation_id}` so every API instance reaches its sockets,
the `presence.heartbeat` every 30 s [TR §8.3], back-pressure, per-event validation with the same
zod schemas as REST, and a registry where feature modules add their event handlers. Polling is
the fallback [TR §4.2]. No event from [TR §8.3] is implemented here except `presence.heartbeat`;
the gateway ships with an echo event used only by tests.

**Admin SSE hub.** One stream per tab; events filtered server-side by permission and scope; a
30 s polling fallback in the client [ADM §1.6]. The hub (publish, subscribe, filter, heartbeat)
is built here; the Redis channel it uses is not in [DD §14] (GAP-MOD00-12).

**Worker job framework.**

1. The registry in `apps/worker/src/jobs` and the `worker_jobs` table must name the same jobs. A
   test fails when a seeded job has no handler or a handler has no row. Until its owning module
   lands, a job is registered as `pending` in a manifest that names the owner, so the test shows
   progress instead of failing.
2. The worker starts a job only when `worker_jobs.is_active` is true.
3. "Run now" is allowed only when `run_now_allowed` is true; the CHECK already forbids it for
   destructive jobs [SQL].
4. Payloads carry ids only, never secrets or personal data (already the rule in
   `apps/worker/src/platform/job.ts`).
5. Every handler is idempotent; retries use backoff; a job that exhausts retries raises the
   `job.failed` console notification [ADM A04].
6. Scheduled jobs take their cron from one place (GAP-MOD00-02).

Jobs implemented in this module:

| Job                   | Schedule [SQL `worker_jobs`] | What it does                                                                         | Source                                                            |
| --------------------- | ---------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `partitions.ensure`   | monthly                      | Creates the next 3 monthly partitions of the 9 partitioned tables. Exists            | [TR §11], [TR §10.2]                                              |
| `partitions.retain`   | monthly                      | Detaches and archives partitions past retention. Destructive: never run on demand    | [TR §11]                                                          |
| Nightly database dump | nightly                      | `pg_dump` to the R2 `backups` bucket (30-day lifecycle), monthly copy kept 12 months | [TR §4.3], [TR §10.3]; no `worker_jobs` row exists (GAP-MOD00-01) |

The other 67 catalogued jobs (70 rows after migration 0007, TRX-049) belong to the module named
in each row's `module` column.

**Webhook intake.** One pipeline for every vendor route under `/webhooks` [TR §8.2]: read the raw
body, verify the signature through a per-vendor port, insert into `webhook_events` (the unique
key refuses duplicates), acknowledge, enqueue processing. Handlers belong to the owning modules;
`webhooks.retry` is MOD-10's. No webhooks go out from this module [TR §12].

### 4.3 Rules the API must enforce

1. Every error response is `application/problem+json` with `request_id` [TR §8.1].
2. A member query never runs without `set_config('app.user_id', $1, true)` as the first statement
   of its transaction (TRX-033); a request for another member's row returns nothing under RLS
   [TR §8.1], [SQL]. In the v3.4 baseline `profiles_read` returns non-hidden, non-blocked
   profiles to any session, including one with `app.user_id` unset (GAP-DB05-03 in
   [1MM-DB-05](../database/1MM-DB-05-SECURITY.md)); schema change set 0007 makes it default-deny
   (TRX-047). Either way the public surface never queries member tables.
3. The member API connects as `app_api` and cannot run DDL [TR §13.1]; `app_api` has no access to
   `admin_recovery_codes` or `vendor_settings` (`packages/db/roles/roles.sql`).
4. Limits come only from `rate_limit_policies`; no handler passes its own numbers [TR §13.3].
5. If Redis cannot answer within 100 ms, the four policies that carry `lockout_seconds` fail
   closed (503 `dependency_unavailable`); every other policy, `otp.send` included, fails open
   with a warning, and the outage raises an alert (DEC-002, GAP-MOD00-20) [TR §20.2 TRX-062],
   [DD §14].
6. A replayed `Idempotency-Key` never executes the handler twice [TR §13.1].
7. Lists never use OFFSET; an unknown sort field is a 422 [TR §8.1], [ADM §1.4].
8. A write with a stale `If-Match` changes nothing and returns 412 [ADM §1.4].
9. A request that did not come through Cloudflare is refused outside local development [TR §4.3].
10. Query strings are never logged; sampled IPs are truncated to /24 or /48 (CHECK) [TR §14], [SQL].
11. A webhook with an invalid signature is stored with `signature_valid = false` and never
    processed; a duplicate `(provider, event_id)` is acknowledged and ignored [TR §12], [SQL].
12. `/docs` and `/openapi/*.json` are never served in production (existing behaviour in
    `apps/api/src/app.ts`).
13. Staging and production share no database, Redis, bucket or key [TR §4.4].
