This plan covers how product events are collected, where the numbers on the admin overview and
analytics pages come from, and how usability studies are recorded and scored. Open it when you add
or change an analytics event in any app, when a dashboard number is questioned, or when you build
A33, A34 or A35. It is also the home of the single event catalogue ([coordinator ruling R17](1MM-EXE-00-MASTER-PLAN.md#7-coordinator-rulings); every ruling cited below by number is in that section).

## 1. Outcome

- **Member:** nothing is sent to analytics until the member has allowed it; the choice can be
  withdrawn and takes effect at once [TR §14], [TR §16.2]. No message body, code, token or free text
  ever leaves the device as an analytics property [SQL `analytics_events` comment].
- **Website visitor:** no analytics library loads before opt-in; Global Privacy Control counts as
  a refusal [WEB §3.10], [WEB §3.11].
- **Admin:** the overview shows queue, growth and revenue tiles, each with its definition, its
  "as of" time and a link to the records behind it [ADM A33]. Business analytics shows funnel,
  retention, matching health, safety KPIs, revenue and markets, with saved reports and scheduled
  exports to admins only [ADM A34]. A researcher can record a usability session on a tablet and
  read the scorecard against the study's targets [ADM A35].
- **Business:** every success measure in [UF §13] and [PP §18] has one written definition and one
  query; every event name used in any app is in one catalogue with an owner.

### 3.5 Event catalogue and metric registry (ruling R17)

**Naming rule (sourced).** Member-app event names follow `screen.action`, lower case, tied to the
screen code, for example `d1.reaction.like` and `pm8.prompt.save` [TR §14]. Every name must match
`^[a-z0-9_.]{2,80}$` [SQL]. Every screen sends viewed, completed and error events so drop-off can
be seen per screen [UF §13.2], [PP §18.2]. Website events use the snake-case names in
[WEB §3.11].

**Catalogue shape (Recommendation).** One typed registry in `packages/contracts` (module
`analytics`), exported to every app. Each entry has:

| Field          | Meaning                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `name`         | The event name; unique                                                                                                          |
| `surface`      | `mobile`, `web_app`, `site_client`, `site_server`, `api` (written by the server)                                                |
| `screen_code`  | Screen id in lower case as used in the name; the canonical id (for example `D1·F`) is stored alongside. Null for website events |
| `owner`        | Owning module (`MOD-07`)                                                                                                        |
| `trigger`      | One sentence: when it fires                                                                                                     |
| `properties`   | A zod schema; closed (unknown keys rejected); only enums, booleans, counts, ids from catalogues                                 |
| `destinations` | `api` (our `analytics_events`), `posthog`, or both                                                                              |
| `since`        | App or site version that first sends it                                                                                         |
| `status`       | `active` or `deprecated` (with the replacing name)                                                                              |

**Governance.**

1. Standard events are generated, not hand-written: for every screen id in [INV] (kept as a
   screen registry beside the catalogue, **Recommendation**) the catalogue contains
   `<screen>.view`, `<screen>.complete` and `<screen>.error` [UF §13.2]. `complete` is registered only where the screen has a completing action.
2. An action event is added in the same pull request as the code that sends it, by the owning
   module, and reviewed by a code owner. Clients can only call `track()` with a name from the
   generated union, so an unregistered name does not compile.
3. A name is never renamed or reused. A change of meaning is a new name; the old one becomes
   `deprecated` and stays accepted until no supported app version sends it (`app_versions.min_supported`).
4. Property rules: no names, e-mail addresses, phone numbers, free text, message bodies, codes,
   tokens, coordinates, health or faith values, report details [SQL comment], [WEB §3.11],
   [TR §14]. A contract test rejects property schemas that contain an unbounded string.
5. CI checks: every name matches the regex and the `screen.action` rule; every `screen_code`
   exists in the screen registry; no duplicates; every event listed in a module plan's API table
   exists in the catalogue.
6. The catalogue is the API's allow-list: `POST /v1/events` drops unknown names and counts them
   (rule 5 in 4.3).
7. Common envelope fields are set by the pipeline, not by callers: `occurred_at`, `session_id`,
   `platform`, `app_version`, `locale`, `country`, `plan` [SQL].

### 4.3 Rules the API must enforce

1. An event is stored only if the member's current `analytics` consent is granted
   (`v_current_consents`) at the time of the request [TR §8.2], [TR §14]. Otherwise the batch is
   accepted with every event dropped; nothing is written.
2. Withdrawal takes effect on the next request: no cache of consent outlives the request
   (**Recommendation:** read through the same per-request member context as entitlements).
3. Anonymous (P) batches are refused until GAP-MOD18-01 is decided: `consent_records.user_id` is
   NOT NULL, so no consent can be proven without an account.
4. `event_name` must match the schema CHECK and be in the catalogue; `screen_code` is taken from
   the catalogue, never from the client.
5. Unknown or deprecated-and-expired names are dropped and counted in a log metric; the request
   still succeeds, so an old app version cannot be broken by a catalogue change.
6. `properties` are validated against the event's schema; unknown keys are removed; a string
   longer than the schema allows drops the event.
7. `user_id`, `platform`, `app_version`, `locale`, `country` and `plan` are set by the server from
   the session, never trusted from the body. `occurred_at` is the client time, clamped to the
   request time when it is in the future or older than the retention window; `received_at` is the
   server time [SQL].
8. Events are deduplicated on the client-generated `id` within a batch and across retries
   (**Recommendation:** a short-lived Redis set of seen ids, never a column or a property; the
   key is added to [DD §14] with GAP-MOD18-03).
9. Rows are append-only: no update or delete path exists except partition retention at 13 months
   and member erasure [TR §16.1].
10. Erasure (`erasure.run`, MOD-16) removes or detaches a member's rows: the port is defined
    here and called by MOD-16.
11. Every analytics response is aggregated. No endpoint in this module returns a member id, and
    `analytics_saved_reports.query` is refused if it contains one [SQL comment].
12. A cell with fewer than 10 members is returned as suppressed ("<10") in views and exports,
    and totals are not shown where they would reveal a suppressed cell [ADM A34], [ADM §4].
13. A tile the admin lacks permission for is absent from the overview response, not zeroed
    [ADM A33]. The viewing admin's country scope is applied to every query [SQL comment].
14. MAU is a distinct count over 30 days from `analytics_events`, not a sum of daily counts.
15. The overview refuses a custom range longer than 90 days [ADM A33].
16. Period tiles return the materialised view's last refresh time as `as_of` [ADM A33].
17. No tile or chart returns a value without a registered definition [ADM A33].
18. Scheduled-export recipients must be active admin users; an external address is impossible by
    type (`recipient_admin_ids`). A recipient who has lost `analytics.read` is skipped and the skip
    is written to the run's audit row [ADM A34] (**Recommendation** for the skip rule).
19. `run_weekday` is required for weekly and `run_monthday` (1–28) for monthly schedules;
    `next_run_at` is computed in the schedule's `timezone` [SQL].
20. Deleting a saved report deletes its schedules (FK cascade) and is audited for both.
21. A session accepts all ten SUS answers or none; each is 1–5; `trust_score` is 0–10 [SQL],
    [ADM A35].
22. A session cannot be completed until every task of the study has a result [ADM A35].
23. The API never computes the SUS score for storage: the generated column is the only source.
    The client preview uses the same formula and a shared test vector proves they agree.
24. Task success counts only `outcome = 'success'` with no critical error [SQL view].
25. The pass bar is false while any finding has `mentioned_by >= 3` and `status <> 'fixed'`
    [ADM A35].
26. `risk_accepted_at` may be set only when `status = 'wont_fix'` [SQL].
27. Research exports contain pseudonyms only; no export joins a participant to a member
    [ADM A35].
28. One session per participant per study [SQL UNIQUE].

- **Website (`apps/site`).** A small analytics module exposes `track(name, properties)` typed

  stops sending and removes the library's storage. Server-side counts need no client code.
- **Billing web app (`apps/web`).** Signed-in members only. It uses the same `track()` wrapper
  and `POST /v1/events` with `platform = 'web'`, gated by the member's consent. Its events are the
  billing events of MOD-10's catalogue rows.

## 7. Mobile: what it adapts and uses

No screen is owned. The module delivers one analytics client in `apps/mobile` used by every
screen:

- `track(name, properties)` accepts only catalogue names. Standard `view`, `complete` and `error`
  events are sent by the screen wrapper from the route's screen code, so screens do not repeat
  them.
- Nothing is initialised before consent. After consent the client (a) queues events in the MMKV
  outbox and sends them in batches to `POST /v1/events` on a timer, on background and on resume
  [TR §15.2], and (b) forwards the same events to PostHog Cloud [TR §5.1].
  Sending to both from one wrapper is a **Recommendation**; the source names both destinations.
- Offline: events stay in the outbox with their original `occurred_at`; the outbox is capped and
  drops the oldest events first. Data-saver mode lengthens the batch interval.
- Withdrawal: the outbox is cleared, the PostHog client is reset and shut down.
- Sign-out and account switch reset the session id; no identifier survives sign-out.
- No analytics call may block or delay a screen; failures are silent and never shown.
- Phone and tablet: identical behaviour.

Where the member gives or withdraws this consent is not on any board: GAP-MOD18-01. Until it is
decided the client ships with analytics off for everyone, and the dashboards rely on the
server-side tables.
