**What this document is for and when to open it.** It is the threat model of 1minitman: what we
protect, where trust changes hands, the attacks we expect and the control that answers each one,
with the place it is built and whether it exists yet. It also lists the privacy-law duties the
sources state, the incident response outline and the security checklist for pull requests. Open it
before you design an endpoint, when you review a change to auth, payments, admin or media, and when
an incident starts.

Legal statements in section 6 repeat what the sources say. Anything marked **Counsel** is legal
interpretation that the lawyer engaged under [OD-10] must confirm. Nothing here is legal advice.

## 3. Actors and trust boundaries

**Actors:** anonymous internet client; website visitor; signed-in member (Free, Premium, Gold; any of
them may be hostile: scammer, stalker, scraper, minor); trusted contact (no account, holds a link
token); admin (ten seeded roles, scoped grants [TR §7.2]); a malicious or compromised insider; a
vendor sending webhooks; a compromised dependency or CI runner; the worker.

| #    | Boundary                                                                      | What crosses it                      | Control at the boundary                                                                                                                                         | Source                        |
| ---- | ----------------------------------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| TB1  | Internet → Cloudflare edge                                                    | All HTTP and WebSocket traffic       | DDoS protection, WAF managed and rate rules, IP lists                                                                                                           | [TR §4.3], [OD-06]            |

## 4. Threat register

**How to read it.** _Cost_ is what a successful attack would cost us or a member. _Where_ names the
module plan that builds the control (links below), the schema object, or the repo control that
already exists. _Status_ is one of:

- **In place**: exists in the repo today (code, CI check, ruleset, role or schema constraint).
- **Schema in place; MOD-nn**: the database rule exists in `packages/db/migrations/0001_baseline_v3_4.sql`; the API behaviour is planned in that module.
- **Planned in MOD-nn**: nothing exists yet; the module plan owns it.
- **Gap**: not covered by a source; see section 10.

### 6.4 Payment scope

No card data touches our servers: the apps use the store sheets through RevenueCat and the web app
uses Flutterwave hosted checkout [TR §13.4], [OD-14]. We store a Flutterwave token reference, card

and needs an owner decision first. **Counsel / provider:** the PCI self-assessment type that

## 7. Incident response outline

`contained` → `resolved` → `post_mortem` [SQL].

| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1. | Playbook                 | Containment                                                                                                                                                    | Source                |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |

## 8. Security review checklist for pull requests

Use it for any pull request that touches `apps/api/src/modules/**/auth*`, sessions or tokens,
billing or webhooks, anything under `/admin/v1`, `packages/db`, `packages/contracts`,
`packages/entitlements`, media upload or processing, or `.github/`. The reviewer ticks each line or
writes why it does not apply.

**Every such pull request**

- [ ] Every input (path, query, header, body, WebSocket frame, webhook body) is parsed by a strict zod schema from `packages/contracts`; unknown keys are rejected (THR-45).
- [ ] Every id taken from the request is checked for ownership, participation or admin scope in the application layer; RLS is not the only check (THR-43).
- [ ] The endpoint has a named rate-limit policy that exists in `rate_limit_policies`, keyed on the right subject (THR-15).
- [ ] Gates are evaluated on the server from entitlements or permissions; nothing trusts a client-sent role, plan, price or flag (THR-37, THR-38).
- [ ] Writes that can be retried carry an idempotency key or client id, and "only one" rules rely on a database constraint (THR-41, THR-50).
- [ ] No secret, token, code, password, message body, face data or card data is logged, put in a URL, an analytics event, a job payload or an error (THR-51).
- [ ] No string-built SQL; no server-side fetch of a user-supplied URL; no `dangerouslySetInnerHTML` (THR-46 to THR-48).
- [ ] Errors are problem+json per [1MM-STD-13](1MM-STD-13-ERROR-CODES.md) and reveal nothing about whether an account, e-mail or row exists (THR-04).
- [ ] Tests cover the hostile cases: another member's id, a missing gate, a replay, an over-limit burst, a malformed body.
- [ ] No new dependency without a reason in the description; `pnpm-lock.yaml` changes are explained (THR-61).

**Auth and sessions**

- [ ] Passwords only through Argon2id and the breached-password check; codes and tokens stored hashed (THR-01, THR-06, THR-11).
- [ ] Lockouts are written to `account_lockouts` as well as Redis (GAP-STD11-05).
- [ ] Session revocation paths set both `sessions.revoked_at` and `sess:deny:{session_id}` (THR-05).
- [ ] Sensitive account changes require re-authentication within 5 minutes (THR-10).
- [ ] Responses for known and unknown identifiers are indistinguishable in body, status and timing (THR-04).

**Payments and webhooks**

- [ ] The webhook handler verifies the signature before parsing, stores the event once, and re-fetches provider state before any grant (THR-35, THR-36).
- [ ] Amounts are integers in minor units from the server-side `prices` row ([1MM-STD-15](1MM-STD-15-DATA-STRUCTURES-AND-MODELS.md) §2.4).
- [ ] Grants are written only through `entitlement_grants` and `refresh_member_role()`; `ent:{user_id}` is deleted (THR-37).
- [ ] Admin refunds go through `admin_approvals`; nothing bypasses `refund_approval_guard()` (THR-39).
- [ ] No code path receives, stores or logs a full card number or CVV (THR-42).

**Admin**

- [ ] The route names its permission; the permission's `requires_reason`, `requires_reauth` and `requires_approval` flags are honoured by the server, not only by the UI (THR-53, THR-56).
- [ ] Scope is applied to lists and direct reads; out-of-scope rows return 404 (THR-44).
- [ ] One `admin_audit_log` row is written in the same transaction for every write, PII reveal and evidence view, with masked personal fields (THR-55, THR-57).
- [ ] Personal fields are masked by default in the response; a reveal is a separate, audited call (THR-55).
- [ ] No personal data is written to browser storage ([1MM-STD-12](1MM-STD-12-DATA-HANDLING.md) §4).

**Database and infrastructure**

- [ ] A new table has its PII class, retention rule, erasure and export manifest entry, and (if member-readable) an RLS policy ([1MM-STD-12](1MM-STD-12-DATA-HANDLING.md), ruling R23).
- [ ] A new append-only ledger is added to the `REVOKE UPDATE, DELETE` list in `packages/db/roles/roles.sql`.
- [ ] A new environment variable is in `.env.example`, has no client prefix unless it is public, and passes `pnpm check:client-bundles`.
- [ ] Workflow changes keep `permissions: contents: read` and commit-hash pins (`pnpm check:repo`).
