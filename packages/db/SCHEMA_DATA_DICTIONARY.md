# 1minitman · Schema data dictionary · v3.4 (21 Nov 2026)

Companion to `schema.sql` v3.4 (same folder). It covers each domain's tables: purpose, key columns, the screens that read (R) or write (W) them, retention and PII class, plus the Redis keyspace.

**Sources:** the owner decisions log (`_sources/DECISIONS_LOG.md`, OD-01 to OD-11 of 18 Nov 2026, OD-12 to OD-31 of 19–20 Nov 2026 and OD-32 to OD-40 of 21 Nov 2026) overrides everything else. The design data review of 21 Nov 2026 (`_sources/DESIGN_DATA_REVIEW_2026-11-21.md`) lists every v3.4 change by item id (M mobile, W website, A admin A01–A18, B admin A19–A36). After it, CHANGE_BRIEF (18 Nov 2026) is the deciding document. Also used: UI_INVENTORY v233 (154 live screens), CANVAS_NOTES v233 and the MVP schema v1.1.

**Verification:** `schema.sql` v3.4 was run on PGlite 0.5.14 (PostgreSQL 18.6 compiled to WebAssembly), with PostGIS, citext and pgcrypto. All 1,183 statements applied. The 37 v3 behaviour tests, 22 v3.1 / v3.2 tests, 4 v3.3 tests and 15 v3.4 tests all passed, and v3.3 plus migration `0005_v3_4_design_review.sql`, applied twice, is identical to a fresh v3.4 (see section 15). PGlite is not PostgreSQL 16 server. The file avoids PG17+ features on purpose: it uses sequences, not identity columns, on partitioned tables (with one exception: `edge_security_events`, added in v3.4, declares `id bigint GENERATED ALWAYS AS IDENTITY`, which PostgreSQL 16 accepts on a partitioned parent; partitions do not inherit the identity property, so inserts always go through the parent, TRX-043), and its own `uuid_v7()` instead of the native `uuidv7()`. Even so, CI must re-run it on a real PostgreSQL 16 + PostGIS 3.4 container before beta.

## Conventions

**Primary keys**

- Entity rows use `uuid_v7()`. These ids are time-ordered, unique across Citus shards, and can be generated on the device for the offline outbox.
- Catalogues use smallint or text keys.
- Append-only logs that nothing references use bigint sequences.

**PII class**

- **none**: no personal data.
- **personal**: identifies or relates to a member.
- **sensitive**: health, faith, live location during a date, credentials, safety incidents.
- **biometric**: face templates and liveness media.

**Retention:** "account" means kept while the account exists. After a deletion request, it is erased 14 days later by job `erasure.run`, unless a longer legal basis is stated.

**Screen codes** are the canvas IDs (D1, PM8, BL1, ...). "API" means the row is written server-side, with no screen of its own.

### Row-level security (sketch)

RLS is enabled on profiles, reactions, conversation_participants, messages, inbox_items, consent_records, trusted_contacts, blocks, data_export_requests and (v3.1) reverification_requests, where a member can read only their own request.

- The member API runs as `app_api` and sets `SET LOCAL app.user_id` for each transaction. Workers and the admin API use roles with BYPASSRLS.
- `is_blocked_pair()` is SECURITY DEFINER, so the profile policy can see blocks in both directions.
- Migration 0007 (section 13C): `profiles_read` returns no row when no member context is set (SC-05); `is_blocked_pair()` pins `search_path = public, pg_temp` and is executable only by `app_api`, `app_admin_api` and `app_worker`; `record_reaction()`, `undo_reaction()`, `decide_intro()` and `unmatch()` are SECURITY DEFINER with an actor guard (SC-02, SC-06), because the member role could not run them under these policies.
- Tested: a member sees only their own inbox rows and only the messages of threads they are in.

### 13B.3 Rules and functions

- **Audit chain v2 (A1, A2).** `admin_audit_chain()` takes the advisory lock, then draws `chain_seq`; the chain walks `chain_seq`. `admin_audit_row_hash(prev, to_jsonb(row))` is the one formula used by the trigger and the verifier. Results of each check go to `admin_audit_chain_runs`.
- **Config approval per key (A3).** `enforce_config_approval()` reads the approval permission from the **old** row's `remote_config.permission_key`, so changing the key itself needs approval. The sanctions ladder (`safety.sanctions_ladder`) is approved under `sanctions.manage`; the ladder JSON gains per-category look-back, a `contact_details` category and steps with hours (A20; only warn / restrict / suspend / ban).
- **T-7 timings (M19).** `unmatch()` reads `unmatch.cooldown_days`; the API applies `intro.text_max_chars` and `dm_request.expiry_days`, whose column literals stay as the seeded defaults.
- **Revenue (B3).** `mv_revenue_daily` counts `environment = 'production'` only and gains a member-country column.
- **One live subscription (B70, OD-37).** `uq_subs_one_live` covers trialing, active, grace, **on_hold**, cancelled (until period end) and paused.
- **Closed beta (W5).** `redeem_beta_invite(code_hash, user)` redeems a `sent`, unexpired invite once and refuses the rest.
- **Legal documents (B38, B39).** `legal_published_immutable()` refuses any edit of a published version and any return to draft; terms, privacy, guidelines, biometric notice and offer terms need a counsel reference to publish.
- **Break-glass (A10).** One break-glass admin account; its grants last at most 4 h.
- **IP rules (B52).** A deny rule needs an expiry within 90 days.
- **Ticket priority (B33).** Higher number = more urgent, as moderation cases (OD-27).

### 13C.2 Rules and functions

- **Move-on cooldown from config (SC-02, TRX-044).** `decide_intro()` reads `discovery.pass_memory_days` (seeded 30) for the cooldown it writes both ways when a member moves on, instead of the literal 30 days. With the seed the behaviour is unchanged; `unmatch()` already read `unmatch.cooldown_days` the same way.
- **Matching functions run as definer (SC-02, SC-06, TRX-048).** `record_reaction()`, `undo_reaction()`, `decide_intro()` and `unmatch()` are `SECURITY DEFINER` with `search_path = public, pg_temp`; `EXECUTE` is revoked from `PUBLIC` and granted to `app_api` and `app_worker` in `roles/roles.sql`. Reason: under the member role's policies the reaction upsert and the undo had no UPDATE policy, `cp_own` refused the other member's participant row on both-keep, and `blocks_own` hid a block placed by the target, so these functions could not run correctly as `app_api`. Bodies are otherwise the baseline bodies.
- **Actor guard.** Because a definer function bypasses row-level security, each of the four checks the caller first. With a member context (`app.user_id`) the actor argument must equal it, otherwise SQLSTATE 42501 "actor mismatch". With no member context the call is allowed only for a login that bypasses row-level security anyway (the worker and admin logins) or that is, or belongs to, the function's owner (migrations); any other login, that is the member API without a member context, gets 42501 "member context required". This last rule is stricter than the change set as first written (which let any caller without a context through) and is recorded as a deviation in the extensions log.
- **`profiles_read` denies by default (SC-05, TRX-047).** The policy now starts with `app_current_user_id() IS NOT NULL`: with no member context it returned every non-hidden profile and now returns none. With a context it is unchanged (own row, or not hidden and not a blocked pair).
- **`is_blocked_pair()` hardened (SC-05, TRX-047).** `search_path = public, pg_temp` (was `public`), `EXECUTE` revoked from `PUBLIC` and granted to `app_api`, `app_admin_api` and `app_worker`, so other roles can no longer test whether two members blocked each other.
- **Run order.** `pnpm db:roles` must follow `pnpm db:migrate`: between the two the application roles cannot execute the five functions above.
